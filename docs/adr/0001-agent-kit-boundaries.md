# User-controlled identities for the Gossip Agent Kit

The design interview settled that v1 creates or reuses a dedicated identity wallet for Gossip authentication, with no funding or transaction tools. Keys remain under user control on the agent host or a user-controlled signer, rather than being held by Gossip; this accepts more setup work in exchange for avoiding Gossip custody. Separate agent installations receive separate identities by default, with deliberate reuse available because sharing also shares private contribution access and earned access.

Installation and connection are distinct outcomes: tools can be installed while connection is pending, and a connection is confirmed only after a signed agent_access request succeeds. These are agreed design constraints, not implemented capabilities; implementation is specified in Gossip issue #1.

The next interview round accepted storage on a user-controlled agent host, including the Grok Bot cloud computer, for the identity-only wallet. A shared host is a shared trust boundary: separate identities provide attribution without promising isolation between Bots that can access the same files. An encrypted backup/restore tool must keep secrets out of chat. A missing wallet must never be silently replaced; a new identity does not inherit prior access.

Consultation and checking own receipts are enabled by default. Private Gossip submission requires explicit authorization, with an optional standing permission defining permitted content. Installation uses a specific release with verified integrity; reruns preserve wallet and configuration, and upgrades are explicit. Grok Bot, Hermes and OpenClaw are all v1 acceptance targets, with tested versions documented and unsupported environments reported rather than improvised around.

Unattended operation after restart is the target, using protected host credential storage where supported. Setup must report unsupported secure storage rather than silently use plaintext key files. Runtime storage and encrypted portable backup are separate concerns. Standard consultations are the default; automatic enriched consultations require an explicit daily earned-credit budget. Local disconnect stops the bridge and removes the integration but preserves the wallet; deletion is explicit and separate, and local disconnect does not revoke copies of a key.

The kit will have its own public repository and versioned releases, independently installable from the engine, with compatibility tests against the engine signing contract. Newly authored kit code is intended for Apache-2.0 licensing, subject to ownership and existing-license checks, with dependency licenses preserved. Keep kit implementation and these design records separate from the website PR.

The toolkit exposes only Gossip operations, constructs requests itself and signs only for the configured endpoint and audience. It exposes no arbitrary-message signing or transaction tool. Submission permissions and earned-credit budgets are enforced by executable toolkit policy, not solely by skill instructions; permission changes use a separate user-controlled configuration step. This enforcement does not promise resistance to another process with equivalent host privileges, consistent with the shared-host boundary above.

Retries preserve a durable logical operation ID while using a fresh authentication nonce and proof. Budget accounting survives restarts and coordinates concurrent operations; uncertain outcomes remain conservatively accounted for until reconciled, without inventing a server reconciliation capability. Exact reconciliation behavior must be verified against the engine contract during implementation.

A clearly labeled developer preview may precede the public endpoint. The public copy-paste connection promise is gated on an available public endpoint and verified end-to-end setup on Grok Bot, Hermes and OpenClaw. Localhost remains an explicit development option. The user accepted recommendations Q1–Q18; the user confirmed the consolidated design and requested the public repository and specification. This document records the approved design; it does not establish a working kit or deployed endpoint.

The reviewed engine automatically selects enriched consultations and has no standard-only request option. Full enforcement requires a coordinated contract extension; the kit must not treat a preflight check as an atomic guarantee. See the compatibility dependency in Gossip issue #1.

The accepted scope in issue #1 subsequently added ERC-8128, ERC-8004 metadata/association, the concrete EIP-712 AgentWalletSet proof, ERC-1271 existing-account validation, and EIP-55. Existing contract-wallet onboarding requires a compatible engine; it must not silently create a new EOA. These additions do not authorize transactions or contract deployment. See docs/acceptance.md for implementation evidence and remaining work.
